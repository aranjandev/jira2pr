# jira2pr

`jira2pr` is a **multi-agent framework** for AI-assisted feature development: read a JIRA ticket, plan, implement, review, and submit a PR. It's lightweight, transparent, and designed for developer supervision at every step.

## Motivation

This framework is for two use cases:

1. **Start a new project:** You have a feature idea and want AI agents to help build it, organized with JIRA tracking and standard git workflows.
2. **Enhance an existing repo:** You've inherited a codebase and want to equip it so agents can add features while maintaining the same discipline.

## What It Is and Is Not

**It is:**
- A simple, transparent workflow framework for AI-assisted development
- Designed for human supervision and intervention at every step
- Runtime-agnostic and built for any codebase

**It is not:**
- A substitute for heavy orchestration frameworks (like [LangChain/LangGraph](https://www.langchain.com/blog/deep-agents-vs-langchain-vs-langgraph) or [CrewAI](https://docs.crewai.com/v1.15.20/en/introduction))
- A replacement for cloud-based agents (like [Copilot Cloud](https://docs.github.com/en/copilot/concepts/agents/cloud-agent/about-cloud-agent))

## How jira2pr Works

`jira2pr` uses a **canonical definitions** model: all agents, skills, workflows, and instructions are defined once in `canonical/` in a platform-agnostic format. The **assembler** (`scripts/assemble.py`) reads these definitions and generates platform-specific output (agent files, prompts, instructions) tailored for VS Code, Claude Code, Cursor, etc.

When you run the assembler, it:
1. Reads canonical agent, skill, and workflow definitions
2. Adds platform-specific frontmatter and formatting
3. Generates a ready-to-use setup folder with slash commands, state management, and artifacts tracking
4. Writes everything to your target directory

This means: **edit canonical sources once, generate for any platform.** Generated output can always be deleted and regenerated.

## Getting Started

### Install jira2pr
1. Clone this repository.
2. Generate the setup files for your platform:
   ```bash
   python scripts/assemble.py --target-dir examples-autogenerated/vscode-copilot --platform copilot
   ```
3. Copy the output folder contents into your project's root.
   ```bash
   cp -R examples-autogenerated/vscode-copilot/.github <your-project-root>/.github
   ```
4. Follow the README in the generated folder to set environment variables and customize your project.
5. Fill in all `<!-- CUSTOMIZE: ... -->` markers with your project-specific details.
6. Use the slash commands (e.g., `/feature`, `/bugfix`) in your AI chat to start a workflow.

#### Verify setup is up to date
```bash
python scripts/assemble.py --target-dir examples-autogenerated/vscode-copilot --platform copilot --check
```

### Set required credentials in .env

The agents read JIRA tickets and make PRs using JIRA and Bitbucket API. You need to provide credentials so it works seamlessly.

1. Copy `.env.example` file to `<project-root>/.env` 
1. Add JIRA details 
1. Add Bitbucket or Github details (whichever is applicable)

### Update repo specific agentic instructions

Agentic frameworks need a markdown with all the necessary instructions for AI agents to work on this repo. Different platforms require different default filenames for this: e.g.
- Github Copilot:  `<project-root>/.github/copilot-instructions.pd` 
- Claude code: `<project-root>/CLAUDE.md` 
- Open Code: `<project-root>/AGENTS.md` or `<project-root>/CLAUDE.md`

After you assembled the setup, a template instruction file is generated in the appropriate location. You need to update that file with repo specific details. The recommended way to populate this is to:
1. Use your existing agent (e.g., Github Copilot) to populate the template. Ask the agent to populate the repo specific details (for repos with existing contents) or populate it with best practices for the type of project you are starting. 
1. Review and refine the agent generated instructions file.

### Creating a JIRA Ticket

Before starting a workflow, create a structured JIRA ticket. Use this template to ensure agents can extract requirements effectively:

```markdown
## Description
<What problem are we solving? Include user/business context and current pain point.>

## Requirements
- <Functional requirement 1>
- <Functional requirement 2>
- <Any important non-functional requirement: performance, security, compatibility>

## Acceptance Criteria
- Given <context>, when <action>, then <expected result>
- Given <context>, when <action>, then <expected result>

## Subtasks
- <Subtask 1>
- <Subtask 2>

## Related Issues
- <Blocks/Depends on/Relates to>: <PROJ-456>

## Implementation Hints
- <Known technical constraints>
- <Relevant service/component/file paths>
- <API contracts, payload examples, or links>

## Additional Notes
- Plan approval required: <Yes/No> # Yes -> agent asks for permission to proceed after presenting the plan. No -> Agent proceeds to implementation after planning.
```

## How It Works

**Workflow phases:** Plan → Implement → Review → Submit → Ready

**State tracking:** Workflow context is stored in a git-tracked state file (`.github/state/<TICKET-KEY>.md`). This allows you to resume from interruptions — pass a PR link to agents and they'll pick up where they left off.

**Scope injection:** Use `/scope-creep` during an active workflow to add additional work without restarting. The agents will plan and implement the delta against the existing plan.

**Built-in QA:** The Review phase includes automated risk detection (breaking changes, missing error handling, security concerns, performance regressions).

**Artifact registry:** Every completed workflow is logged in `.github/artifacts/REGISTRY.md` with timestamps, PR links, and risk levels.

**Slash commands:**
- `/feature` — Full feature workflow (start fresh or resume)
- `/bugfix` — Bugfix workflow (start fresh or resume)
- `/review` — Self-review current changes
- `/scope-creep` — Inject additional work mid-workflow

## Important Notes

- **No runtime dependencies.** All canonical definitions live in `canonical/`; generated output can be deleted and regenerated anytime.
- **Edit only in `canonical/`.** Never edit generated output directly — always edit source files and re-run the assembler.
- **Built for transparency.** All workflow state is human-readable, git-tracked, and interruptible. You can inspect or modify any file at any time.
