# Jira2PR Platform Strategy: GitHub Copilot and Aider

## Overview

The new Jira2PR architecture cleanly separates:

```text
Canonical Definitions
    ↓
Platform Adapters
    ↓
Generated User Repo Assets
```

The canonical layer defines:

```text
Who does work?      → agents/
What gets produced? → artifacts/
When work happens?  → workflows/
How work is judged? → supervisor.yaml
How work resumes?   → workflow-state.template.yaml
```

Platform adapters only determine how those concepts are exposed to a particular execution environment.

---

# Architectural Layers

```
canonical/
├── agents/          # behavior
├── artifacts/       # output contracts
├── capabilities.yaml # external dependencies
├── workflows/       # orchestration
├── state/           # runtime state template
├── model-tiers.yaml # model selection policy
└── project-instructions.md
```

## 1. Canonical Layer

Source of truth:

```text
canonical/
├── agents/
├── artifacts/
├── state/
└── workflows/
```

No platform-specific logic should live here.

For example:

```text
canonical/agents/planner.md
```

defines planner behavior.

```text
canonical/artifacts/plan-schema.md
```

defines planner output.

```text
canonical/workflows/feature.workflow.yaml
```

defines when planner executes.

These files should remain unchanged regardless of:

- Copilot
- OpenCode
- Aider
- Claude Code
- Cursor
- Future platforms

---

## 2. Runtime Layer

Runtime services live in:

```text
runtime/
├── fetch_jira.py
├── git_helper.py
└── pr_helper.py
```

These are deterministic integrations.

They are not AI agents.

Examples:

```text
Fetch JIRA ticket
Create commit
Push branch
Create PR
Update PR
```

These functions should eventually grow into:

```text
runtime/
├── integrations/
│   ├── jira.py
│   ├── git.py
│   └── github.py
│
├── workflow/
│   ├── loader.py
│   ├── executor.py
│   ├── transitions.py
│   └── state_manager.py
│
└── artifacts/
    └── storage.py
```

---

## 3. Platform Adapter Layer

* Platform adapters transform canonical definitions into platform-specific files.
* This layer specifies how to convert a capability to a runtime executable or callable depending on the target platform


Current location:

```text
compiler/assembler/platforms/
├── copilot.py
└── opencode.py
```

Future:

```text
compiler/assembler/platforms/
├── copilot.py
├── opencode.py
├── aider.py
└── claude.py
```

# GitHub Copilot Strategy

## Execution Model

GitHub Copilot remains largely agent-driven.

Generated artifacts:

```text
.github/
├── agents/
├── instructions/
└── prompts/
```

A supervisor agent acts as the workflow interpreter.

Workflow execution:

```text
Supervisor Agent
       ↓
Read feature.workflow.yaml
       ↓
Invoke jira-reader
       ↓
Evaluate outcome
       ↓
Transition
       ↓
Invoke planner
       ↓
...
```

---

## Generated Assets

Assembler target:

```text
examples-autogenerated/
└── vscode-copilot/
```

Generated repository output:

```text
.github/
├── agents/
│   ├── jira-reader.agent.md
│   ├── planner.agent.md
│   ├── coder.agent.md
│   ├── reviewer.agent.md
│   ├── pr-author.agent.md
│   └── supervisor.agent.md
│
├── instructions/
│   └── copilot-instructions.md
│
└── workflows/
    └── copied workflow definitions
```

---

## Supervisor Ownership

For Copilot:

```text
supervisor.agent.md
```

becomes the workflow interpreter.

Responsibilities:

```text
Read workflow definition
Invoke next worker
Validate outputs
Apply transition logic
Handle retries
Handle escalation
```

The workflow remains externalized in YAML.

The supervisor contains no workflow-specific state machine definitions.

---

## Copilot State Management

Workflow state lives in:

```text
.jira2pr/state/
    PROJ-123.yaml
```

not in:

```text
.github/
```

This keeps state platform-independent.

Supervisor reads state.

Runtime updates state.

Workers never modify state directly.

---

# Aider Strategy

## Execution Model

Aider uses a workflow runtime.

Unlike Copilot:

```text
No supervisor-driven orchestration.
```

Instead:

```text
Python Runtime
       ↓
Feature Workflow
       ↓
State Machine Execution
       ↓
Agents
```

The workflow engine owns orchestration.

---

## Generated Assets

Assembler target:

```text
examples-autogenerated/
└── aider/
```

Generated repository output:

```text
.jira2pr/
├── workflows/
├── state/
├── agents/
├── artifacts/
└── runtime/
```

plus:

```text
tools/
└── jira2pr_runner.py
```

or:

```text
.jira2pr/runtime/
└── runner.py
```

---

## Workflow Engine

Aider runtime becomes the primary implementation target.

Core modules:

```text
runtime/workflow/
├── loader.py
├── executor.py
├── state_manager.py
├── transitions.py
├── worker_invoker.py
└── supervisor_invoker.py
```

Responsibilities:

```text
Load workflow YAML
Load workflow state
Invoke agents
Invoke supervisor
Validate outputs
Apply transitions
Persist state
Resume execution
```

---

## Worker Invocation

Aider uses canonical agent definitions directly.

Example:

```text
canonical/agents/planner.md
```

is loaded as:

```text
SYSTEM PROMPT
```

No generated:

```text
planner.agent.md
```

is required.

Invocation flow:

```text
planner.md
    +
plan-schema.md
    +
requirements.md
    +
repository context
```

↓

```text
LLM
```

↓

```text
plan.md
```

---

## Supervisor Invocation

Runtime invokes:

```text
canonical/agents/supervisor.md
```

with:

```text
supervisor.yaml
success criteria
artifacts
```

Expected output:

```json
{
  "outcome": "success",
  "reason": "...",
  "feedback": "...",
  "violations": []
}
```

Runtime validates response.

Runtime owns transitions.

Supervisor owns evaluation.

---

# State Management

## Canonical Template

```text
canonical/state/
└── workflow-state.template.yaml
```

Example instance:

```text
.jira2pr/state/
└── PROJ-123.yaml
```

Created automatically.

Never edited by workers.

---

## Ownership Model

| Component | Writes State |
|------------|------------|
| jira-reader | No |
| planner | No |
| coder | No |
| reviewer | No |
| pr-author | No |
| supervisor | No |
| runtime engine | Yes |

State transitions occur only after:

```text
worker execution
      +
supervisor outcome
```

# Assembler Architecture

The assembler is responsible for transforming canonical workflow definitions into platform-specific repository assets.

```text
canonical/
        ↓
   assemble.py
        ↓
 platform adapter
        ↓
generated package
```

The assembler never interprets workflow behavior.

Its responsibility is limited to projection and packaging.

Examples:

```text
canonical/agents/planner.md
```

↓

```text
.github/agents/planner.agent.md
```

or

```text
.jira2pr/runtime/
```

depending on the target platform.

---

## Assembler Components

### assemble.py

Entry point.

Responsible for:

- loading canonical content
- selecting target platform(s)
- creating generation context
- invoking platform adapters

Example:

```bash
python compiler/assemble.py --platform copilot
```

or:

```bash
python compiler/assemble.py --platform aider
```

---

### assembler/registry.py

Loads registries and metadata.

Examples:

```text
canonical/agents/_registry.yaml
canonical/model-tiers.yaml
```

Produces normalized metadata objects used by adapters.

Example:

```python
AgentSpec(
    slug="planner",
    tier=2
)
```

---

### assembler/templates.py

Handles reusable template rendering.

Responsibilities:

- token replacement
- front-matter injection
- README generation
- platform-specific wrappers

Example:

```text
{{PROJECT_INSTRUCTIONS}}
```

↓

```text
contents of project-instructions.md
```

---

### assembler/writer.py

Responsible for file emission.

Responsibilities:

- create directories
- write generated files
- ensure generated output is deterministic

Example:

```python
write(
    ".github/agents/planner.agent.md"
)
```

---

### assembler/base.py

Defines platform adapter interface.

Example:

```python
class PlatformAdapter:

    def generate(self):
        ...
```

All platforms implement the same interface.

## Installation and User Experience

### Installation

Jira2PR is distributed as a Python package and should use **uv** as the preferred installation and environment management tool.

Install globally:

```bash
uv tool install jira2pr
```

Initialize a repository:

```bash
jira2pr init --platform copilot
```

or

```bash
jira2pr init --platform aider
```

The initialization step runs the assembler and generates the platform-specific package for the target environment.

---

### User Interaction Model

Users interact with **workflows**, not individual agents.

Workers such as `planner`, `coder`, and `reviewer` are internal implementation details.

#### GitHub Copilot

Generated assets:

```text
.github/
```

Primary entry points:

```text
/feature PROJ-123
/bugfix PROJ-456
/scope-creep PROJ-789
```

Additional commands:

```text
/resume PROJ-123
/status PROJ-123
```

The supervisor interprets the workflow definition and coordinates worker execution.

---

#### Aider

Generated assets:

```text
.jira2pr/
```

Primary entry point:

```bash
jira2pr run feature PROJ-123
```

Equivalent long form:

```bash
jira2pr run --workflow feature --ticket PROJ-123
```

Additional commands:

```bash
jira2pr resume PROJ-123
jira2pr status PROJ-123
jira2pr list
```

The Python workflow runtime loads the workflow definition, executes workers, invokes the supervisor, updates workflow state, and applies transitions.

---

### Design Principle

The public API of Jira2PR is the workflow:

```text
feature
bugfix
scope-creep
```

Users should never need to invoke:

```text
planner
coder
reviewer
pr-author
```

directly. Workflow definitions are the user-facing abstraction; workers remain internal implementation details.

```text
canonical/
```

## Agent Generation

Source:

```text
canonical/agents/planner.md
```

Metadata:

```text
canonical/agents/_registry.yaml
```

Tier information:

```text
canonical/model-tiers.yaml
```

Generated:

```text
.github/agents/planner.agent.md
```

Example:

```text
---

permissions: ...
```

Source:

```text

```

```text
.github/workflows/
```

```text
canonical/project-instructions.md
```

plus:

```text
canonical/platform-extras/copilot/
```

Generated:

```text
.github/copilot-instructions.md
```

# Aider Generation

## Aider Adapter

Location:

```text
compiler/assembler/platforms/aider.py
```

Unlike Copilot, Aider does not require generated agent definitions.

Therefore the adapter generates a runtime package instead.

Input:

```text
canonical/
runtime/
```

Output:

```text
.jira2pr/
├── workflows/
├── state/
├── artifacts/
├── runtime/
└── config/
```

---

## Runtime Generation

The adapter generates runtime configuration such as:

```text
.jira2pr/runtime/
├── workflow_executor.py
├── worker_invoker.py
├── supervisor_invoker.py
└── state_manager.py
```

These components consume canonical definitions directly.

No Aider-specific copies of:

```text
planner.md
coder.md
reviewer.md
```

are required.

---

## Agent Resolution

At runtime:

```python
load_agent(
    "planner"
)
```

resolves:

```text
canonical/agents/planner.md
```

or its packaged copy.

The Aider runtime uses canonical agent definitions as prompts.

---

## State Management

The adapter copies:

```text
canonical/state/workflow-state.template.yaml
```

into:

```text
.jira2pr/state/
```

The runtime uses this template to create workflow instances:

```text
.jira2pr/state/PROJ-123.yaml
```

during execution.

---

# Long-Term Goal

The assembler should eventually support:

```text
canonical/
        ↓

      DSL

        ↓

 ┌──────────┬──────────┬──────────┐
 ↓          ↓          ↓

Copilot   OpenCode   Aider

agents     agents    runtime
```

The canonical workflow definitions remain unchanged.

Only the packaging and execution model vary by platform.

# Recommended Implementation Order

## Phase 1

Freeze canonical DSL.

Stable:

```text
agents/
artifacts/
workflows/
state/
```

No further restructuring.

---

## Phase 2

Implement workflow loading.

Build:

```python
load_workflow()
load_workers()
load_success_criteria()
load_supervisor_contract()
```

No LLMs yet.

---

## Phase 3

Implement state engine.

Build:

```python
create_state()
load_state()
save_state()
transition_state()
resume_workflow()
```

using:

```text
workflow-state.template.yaml
```

---

## Phase 4

Implement worker abstraction.

Build:

```python
invoke_worker()
```

initially with mocks.

---

## Phase 5

Implement supervisor abstraction.

Build:

```python
invoke_supervisor()
```

Return mocked outcomes initially.

---

## Phase 6

Implement complete workflow execution.

Successfully run:

```text
jira-ingest
    →
plan
    →
implement
    →
review
    →
submit
```

without real LLMs.

---

## Phase 7

Build Aider backend.

This becomes the first real runtime implementation.

The Aider backend will validate:

- workflow DSL
- state model
- artifact model
- supervisor contract

before Copilot/OpenCode adapters are expanded further.

---

# Final Recommended Mental Model

```text
Canonical
    =
    Product

Assembler
    =
    Adapter

Runtime
    =
    Execution Engine
```

The future architecture becomes:

```text
canonical/
        ↓
   assemble.py
        ↓

 ┌─────────────┬─────────────┐
 ↓             ↓             ↓

Copilot     OpenCode      Aider
 Agents      Agents      Runtime

        ↓
    Same Workflows
        ↓
 Same Artifacts
        ↓
 Same Outcomes
```

This maximizes reuse while keeping workflow logic defined exactly once in the canonical DSL.
