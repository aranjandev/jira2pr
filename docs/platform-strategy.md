# Jira2PR Platform Strategy: GitHub Copilot and Aider

## Overview

The new Jira2PR architecture cleanly separates:

```text
Canonical Definitions
    ↓
Platform Adapters
    ↓
Generated User Repo Assets
```

The canonical layer defines:

```text
Who does work?      → agents/
What gets produced? → artifacts/
When work happens?  → workflows/
How work is judged? → supervisor.yaml
How work resumes?   → workflow-state.template.yaml
```

Platform adapters only determine how those concepts are exposed to a particular execution environment.

---

# Architectural Layers

```
canonical/
├── agents/          # behavior
├── artifacts/       # output contracts
├── capabilities.yaml # external dependencies
├── workflows/       # orchestration
├── state/           # runtime state template
├── model-tiers.yaml # model selection policy
└── project-instructions.md
```

## 1. Canonical Layer

Source of truth:

```text
canonical/
├── agents/
├── artifacts/
├── state/
└── workflows/
```

No platform-specific logic should live here.

For example:

```text
canonical/agents/planner.md
```

defines planner behavior.

```text
canonical/artifacts/plan-schema.md
```

defines planner output.

```text
canonical/workflows/feature.workflow.yaml
```

defines when planner executes.

These files should remain unchanged regardless of:

- Copilot
- OpenCode
- Aider
- Claude Code
- Cursor
- Future platforms

---

## 2. Runtime Layer

Runtime services live in:

```text
runtime/
├── fetch_jira.py
├── git_helper.py
└── pr_helper.py
```

These are deterministic integrations.

They are not AI agents.

Examples:

```text
Fetch JIRA ticket
Create commit
Push branch
Create PR
Update PR
```

These functions should eventually grow into:

```text
runtime/
├── integrations/
│   ├── jira.py
│   ├── git.py
│   └── github.py
│
├── workflow/
│   ├── loader.py
│   ├── executor.py
│   ├── transitions.py
│   └── state_manager.py
│
└── artifacts/
    └── storage.py
```

---

## 3. Platform Adapter Layer

* Platform adapters transform canonical definitions into platform-specific files.
* This layer specifies how to convert a capability to a runtime executable or callable depending on the target platform


Current location:

```text
compiler/assembler/platforms/
├── copilot.py
└── opencode.py
```

Future:

```text
compiler/assembler/platforms/
├── copilot.py
├── opencode.py
├── aider.py
└── claude.py
```

# GitHub Copilot Strategy

## Execution Model

GitHub Copilot remains largely agent-driven.

Generated artifacts:

```text
.github/
├── agents/
├── instructions/
└── prompts/
```

An orchestrator agent acts as an extremely simple workflow orchestrator.

Workflow execution:

```text
Orchestrator Agent
       ↓
Read feature.workflow.yaml
       ↓
Invoke jira-reader
       ↓
Evaluate outcome using Supervisor agent
       ↓
Transition
       ↓
Invoke planner
       ↓
...
```

---

## Generated Assets

Assembler target:

```text
examples-autogenerated/
└── vscode-copilot/
```

Generated repository output:

```text
.github/
├── agents
│   ├── _registry.yaml
│   ├── coder.md
│   ├── jira-reader.md
│   ├── orchestrator.md
│   ├── planner.md
│   ├── pr-author.md
│   ├── researcher.md
│   ├── reviewer.md
│   └── supervisor.md
│
├── instructions/
│   └── copilot-instructions.md
│
└── workflows/
    └── copied workflow definitions
```

---

## Supervisor Ownership

For Copilot:

```text
supervisor.agent.md
```

Responsibilities:

```text
Read workflow definition
Invoke next worker
Validate outputs
Apply transition logic
Handle retries
Handle escalation
```

The workflow remains externalized in YAML.

The supervisor contains no workflow-specific state machine definitions.

---

## Copilot State Management

Workflow state lives in:

```text
.jira2pr/state/
    PROJ-123.yaml
```

not in:

```text
.github/
```

This keeps state platform-independent.

Supervisor reads state.

Runtime updates state.

Workers never modify state directly.

---

# Aider Strategy

## Execution Model

Aider uses a workflow runtime.

Unlike Copilot:

```text
No orchestrator-driven transitions.
```

Instead:

```text
Python Runtime
       ↓
Feature Workflow
       ↓
State Machine Execution
       ↓
Agents
```

The workflow engine owns orchestration.

---

## Generated Assets

Assembler target:

```text
examples-autogenerated/
└── aider/
```

Generated repository output:

```text
.jira2pr/
├── workflows/
├── state/
├── agents/
├── artifacts/
└── runtime/
```

plus:

```text
tools/
└── jira2pr_runner.py
```

or:

```text
.jira2pr/runtime/
└── runner.py
```

---

## Workflow Engine

Aider runtime becomes the primary implementation target.

Core modules:

```text
runtime/workflow/
├── loader.py
├── executor.py
├── state_manager.py
├── transitions.py
├── worker_invoker.py
└── supervisor_invoker.py
```

Responsibilities:

```text
Load workflow YAML
Load workflow state
Invoke agents
Invoke supervisor
Validate outputs
Apply transitions
Persist state
Resume execution
```

---

## Worker Invocation

Aider uses canonical agent definitions directly.

Example:

```text
canonical/agents/planner.md
```

is loaded as:

```text
SYSTEM PROMPT
```

No generated:

```text
planner.agent.md
```

is required.

Invocation flow:

```text
planner.md
    +
plan-schema.md
    +
requirements.md
    +
repository context
```

↓

```text
LLM
```

↓

```text
plan.md
```

---

## Supervisor Invocation

Runtime invokes:

```text
canonical/agents/supervisor.md
```

with:

```text
supervisor.yaml
success criteria
artifacts
```

Expected output:

```json
{
  "outcome": "success",
  "reason": "...",
  "feedback": "...",
  "violations": []
}
```

Runtime validates response.

Runtime owns transitions.

Supervisor owns evaluation.

---

# State Management

## Canonical Template

```text
canonical/state/
└── workflow-state.template.yaml
```

Example instance:

```text
.jira2pr/state/
└── PROJ-123.yaml
```

Created automatically.

Never edited by workers.

---

## Ownership Model

| Component | Writes State |
|------------|------------|
| jira-reader | No |
| planner | No |
| coder | No |
| reviewer | No |
| pr-author | No |
| supervisor | No |
| runtime engine | Yes |

State transitions occur only after:

```text
worker execution
      +
supervisor outcome
```

---

# Artifacts

## Human-Owned Artifacts

Generated by workers:

```text

plan.md
review.md
pr-description.md
decision.md
```

These conform to:

```text
requirements-schema.md
plan-schema.md
review-schema.md
pr-schema.md
decision-schema.md
```

---

## Runtime-Owned Artifacts

Generated by execution engine:

```text
workflow-state.yaml
```

Used for:

```text
Resume
Tracking
Retries
Audit history
Artifact discovery
```

canonical/

      DSL

 ┌──────────┬──────────┬──────────┐
 ↓          ↓          ↓
